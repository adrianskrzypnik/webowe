Opis projektu

Tworzymy prostą stronę typu galeria / sklep z dużą liczbą zdjęć, która w wersji bazowej jest celowo nieoptymalna. Na niej wdrażamy kolejno trzy techniki optymalizacji: nowoczesne formaty obrazów, lazy loading oraz code splitting. Każdą wersję mierzymy tymi samymi narzędziami i w tych samych warunkach, a wyniki porównujemy z wersją bazową.

Testowane techniki

1. Formaty i rozmiary obrazówJPG/PNG → WebP / AVIF, srcset z kilkoma rozdzielczościami, kompresja (np. vite-imagetools lub Squoosh)Rozmiar strony, LCP

Techniki zapasowe: minifikacja i kompresja Brotli/Gzip, cache HTTP, preload fontów, wirtualizacja długich list.

Narzędzia

Używamy dwóch narzędzi. Lighthouse mierzy metryki wydajności wszystkich wersji strony. Do code splittingu dochodzi rollup-plugin-visualizer, który mierzy rozmiar bundla JS bezpośrednio z builda.

NarzędzieDo czego
Google Lighthouse (Chrome DevTools)Główny pomiar wszystkich trzech technik: wynik Performance, Web Vitals, rozmiar i liczba zasobów
rollup-plugin-visualizerPomiar code splittingu: rozmiar i skład bundla JS (wersja gzip) przed i po podziale na chunki

Żeby wyniki wersji dało się porównać, testujemy je w tych samych warunkach: profil mobile, łącze Slow 4G (1,6 Mb/s, RTT 150 ms, domyślne w Lighthouse), pusty cache, 5 przebiegów i mediana.

Metryki

Lighthouse mierzy wszystkie metryki z tabeli poza liczbą chunków; visualizer mierzy tylko rozmiar JS i liczbę chunków. Progi „dobrego” wyniku są wg Google.

Pominęliśmy Performance Score, bo jest wynikiem zbiorczym z metryk, które podajemy osobno. INP też pominęliśmy, bo wymaga interakcji prawdziwego użytkownika i Lighthouse nie zmierzy go przy zwykłym załadowaniu strony.
